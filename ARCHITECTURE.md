# Architecture Overview

How OP2Formats is put together: where things live, how data flows from a player's Outpost 2 install to a caller,
and the rules that keep it that way. Keep it current when the layout changes. Day-to-day state and next steps are
in [NOTES.md](NOTES.md); each crate's README has the details of its format.

## 1. Project Structure

## 2. High-Level System Diagram

```
                      the player's Outpost 2 install (GOG / CD + OPU 1.4.1)
              loose files (OPU/base, game folder) · *.vol archives · Outpost2.exe · DLLs
                                          │
                          ┌───────────────▼────────────────┐
  GOG / OPU installers ──►│ op2-formats                    │◄── .map / .prt / .txt bytes from memory
  (extract, install)      │ GameFiles → readers → types    │
                          │ Exe → GameExe (checked tables) │
                          └───────┬───────────────┬────────┘
                                  │ Map           │
                   ┌──────────────▼───┐   ┌───────┴──────┐
                   │ op2-mapjson      │   │ op2-opm      │   (no dependency on op2-formats)
                   │ .map ⇄ JSON map  │   │ .opm ⇄ model │
                   └────────┬─────────┘   └──────┬───────┘
                            │                    │
              ┌─────────────▼────────────────────▼──────────────┐
              │ op2formats-c: op2f_* functions, opaque handles  │
              │ op2formats.dll / .so / .dylib + static library  │
              └─────────────┬───────────────────────────────────┘
                            │ op2formats.h (+ CMake targets)
                     C / C++ / other-language programs
```

Rust programs use the three library crates directly; everything else goes through the C interface.

## 3. Core Components

### 3.1. op2-formats (the readers)

- **What:** pure-Rust readers (and a few writers: `.map`, images) for every Outpost 2 data format, written by bufke
  for op2-rs. Formats follow OutpostUniverse/OP2Utility.
- **Entry point:** `GameFiles::open(dir)` indexes an install the way the game layers it: OPU's loose files first,
  then the game folder, then the `.vol` archives. Readers take a `GameFiles` (`read_map`, `Sprites::open`,
  `Rules::load`, ...) or plain bytes (`Map::parse`, `ArtFile::parse`, ...).
- **Tables from the exe:** `exe::Exe` reads PE sections; `GameExe::of(files)` reads and checks every table the game
  keeps in its code and data (unit art, armor values, sound and music names, build lists, cell types, cursors),
  decoding a few functions' stores with `iced-x86`. It is cached per game folder (`cache::FolderCache`). Nothing
  from the game is embedded in the source.
- **Features:** `inno` and `opu` (installer readers, default on in the C crate), `fetch-opu` (HTTPS download of
  OPU's installer, off).
- **Upstream rule:** the folder is byte-identical to an op2-rs commit (named in README.md; `git rev-parse
  HEAD:op2-formats` equals op2-rs's `<commit>:tools/crates/op2-formats`). Re-syncing means copying the folder again
  and fixing the crates that use it. Fixes to the readers go to op2-rs.

### 3.2. op2-mapjson

- **What:** converts `.map` files to and from OP2MapJsonTools' JSON maps, writing only the PerRowPadded layout,
  byte for byte as that tool does.
- **How:** `MapJson::from_map` reads an op2-formats `Map`; `to_map(base)` builds a skeleton `.map`, parses it with
  op2-formats and fills it in, taking what JSON doesn't carry (version tag, empty tileset slots, tile groups) from an
  optional base map. Unknown JSON members are kept and written back.

### 3.3. op2-opm

- **What:** reads and writes OP2MissionEditor's `.opm` JSON missions; modelled after OP2DotNetMissionSDK's
  `MissionReader/Json`.
- **How:** a lenient reader (`relax()` strips comments and trailing commas, nulls dropped, the legacy top-level
  layout upgraded, case-insensitive enums with an `Other` fallback, unknown members flattened into `extra`) and a
  writer in the editor's layout (CRLF, tabs, sorted keys). Independent of op2-formats.

### 3.4. op2formats-c (the C interface)

- **What:** `extern "C"` functions with the prefix `op2f_`, built as a cdylib, a staticlib and an rlib named
  `op2formats`, covering all three crates.
- **Conventions (also in the header's top comment):**
  - Opaque handles from `op2f_*_open` / `_parse`, released by the matching `_free`; freeing NULL does nothing.
  - Fallible calls return `Op2fStatus`; `op2f_last_error` holds the calling thread's message.
  - Strings out are copied into a caller buffer (`buf`, `cap`, `len`); a NULL buffer asks for the length.
  - Every call runs inside `catch_unwind`: a panic becomes `OP2F_STATUS_PANIC`.
  - A function whose Cargo feature is left out stays exported and returns `OP2F_STATUS_UNSUPPORTED`, so the header
    is the same for every build.
- **Layout:** `src/lib.rs` holds the status codes and the helpers every area uses (`guard`, `obj`, `put`,
  `copy_str`, `index`, ...); each area is one file, re-exported by `lib.rs`. `#[repr(C)]` structs mirror the Rust
  types by value; anything variable-sized stays behind a handle.
- **Header:** generated by cbindgen 0.29.4 and committed; regenerate it after any interface change.

### 3.5. CMake integration

`CMakeLists.txt` runs Cargo for `op2formats-c` (with `OP2FORMATS_FEATURES` and `OP2FORMATS_RUST_TARGET`; MinGW
defaults to `x86_64-pc-windows-gnu`) and defines imported targets `OP2Formats::OP2Formats` (shared unless
`OP2FORMATS_LINK_STATIC`), `::shared` and `::static`, plus `op2formats_copy_runtime(target)`. `cmake --install`
writes a `find_package(OP2Formats)` config from `cmake/`.

## 4. Data Sources

The library stores nothing of its own. What it reads:

| Source | Read by | Notes |
|---|---|---|
| The player's install folder | `GameFiles`, `install` | Found via a path, `$OP2_DIR` or the usual install places; OPU's `OPU/base` loose files win over the game folder's and the `.vol`s' |
| `.vol` archives | `vol`, `lzh` | maps, sheets, sprites, sounds, tilesets |
| `Outpost2.exe` | `exe` | Tables are checked against known shapes; GOG's 1.2.0.7 build is the tested one, another build runs with a warning |
| The game's DLLs | `pe_res` | `out2res.dll` and others: bitmaps, cursors, dialogs, strings |
| GOG's and OPU's installers | `inno`, `nsis`, `opu` | Extracted or installed into a folder the caller names |
| JSON maps and `.opm` files | `op2-mapjson`, `op2-opm` | Written by the user's tools; not game data |

## 5. External Integrations

- **outpost2.net** (feature `fetch-opu` only): downloads OPU's official installer over HTTPS (`ureq` with rustls),
  checked against a pinned SHA-256 before use.
- **Formats shared with other tools:** OP2Utility (the format reference), OP2MapJsonTools / OP2MapViewerJson
  (JSON maps), OP2MissionEditor and OP2DotNetMissionSDK (`.opm`).

## 6. Deployment & Distribution

- **Rust:** path or git dependency on the crates; not on crates.io yet (the crate name is undecided, see NOTES.md).
- **C/C++:** build with Cargo or CMake and ship `op2formats.dll` / `libop2formats.so` / `libop2formats.dylib` (or
  link the static library) with `include/op2formats.h`.
- **CI:** GitHub Actions on Ubuntu, Windows and macOS: build and test the workspace with default and all features,
  without game data (real-data tests skip).
- **Licence:** GPL-3.0-or-later, inherited from op2-rs; a program linking the library, including through the C
  interface, must be GPL as well.

## 7. Security Considerations

- **Untrusted input:** maps, sprites, sheets, installers and JSON can come from anywhere. Readers report bad data
  as errors and bound counts by the bytes left (`Map::parse` checks its header counts before allocating). The C
  layer checks pointers, lengths and indices and turns any panic into a status.
- **Installers:** GOG's installer's file names are refused when they would leave the output folder (`inno.rs`).
  OPU is installed only from an installer whose SHA-256 matches the pinned one (`opu::PACKAGE_SHA256`),
  downloaded or not.
- **No game assets in the repository:** nothing extracted from Outpost 2 is committed; tests read the player's own
  install. The `.opm` fixtures in `op2-opm/tests/data` are the user's own missions.

## 8. Development & Testing Environment

- **Toolchain:** Rust 1.99 via `rust-toolchain.toml`; cbindgen 0.29.4 for the header; CMake 3.19+ and a C/C++
  compiler for the C side (checked with MSVC 2022).
- **Tests:** `cargo test --workspace` (and `--all-features`). Real-data tests need `OP2_DIR` (an install with OPU
  1.4.1) and skip without it; `OP2_REQUIRE_DATA=1` makes a skip a failure. Leave op2-rs's `OP2_REQUIRE_RUNS`
  unset. Optional sample inputs: `OP2_MAPJSON`, `OP2_OPM_DIR`, `OP2_OPU_INSTALLER`.
- **Quality:** `cargo clippy --workspace --all-targets -- -D warnings` with no, default and all features. After a C
  interface change: regenerate the header, compile it as C and C++ with warnings as errors, check struct sizes and
  alignment match between C, C++ and Rust, and that the library exports every declared function (NOTES.md,
  "Checks before a commit").

## 11. Glossary

- **OPU:** the Outpost Universe community update (1.4.1), which patches the game and ships its data as loose files
  under `OPU/base`.
- **`.vol`:** the game's archive format, entries stored raw or LZH-compressed.
- **`.map`:** a map's terrain: tiles (mapping index + cell type), tileset slots, tile mappings, terrain types, tile
  groups. Units come from mission DLLs or `.opm` files, not the map.
- **Tile mapping:** a tileset and graphic index, plus animation, that a map tile points to.
- **Cell type:** a tile's movement and sight class (0-31).
- **Sheets:** the tab-separated rule files (`vehicles.txt`, `weapons.txt`, `building.txt`, ...).
- **`op2_art.prt`:** the sprite metadata (palettes, images, animations, frames) paired with `OP2_ART.BMP`'s pixels.
- **`GameExe`:** every table op2-formats reads from `Outpost2.exe`, checked, cached per game folder.
- **`.opm`:** OP2MissionEditor's JSON mission format.
- **PerRowPadded:** OP2MapJsonTools' JSON map layout with one line per row, numbers aligned in columns.
- **Clip rect:** the part of the map the game lets the view and units reach.
